### Отклонения от плана и почему

- **`paddingEnd` вместо `padding-bottom` у скроллера.** Отступ под последним сообщением теперь участвует в виртуальной модели, иначе он «висит» ниже фолда и искажает определение конца.
- **Стабилизация `estimateSize`/`getItemKey` через `useCallback`.** Внутренний memo виртуализатора ключуется на эти функции; стрелка, создаваемая на каждый рендер, вызывала бы O(count)-пересчёт измерений на каждом кадре скролла.
- **Жест на обёртке, а не на скроллере.** Скроллер остаётся `role="log"` без интерактивной семантики; события всплывают от него к `.message-scroll-wrap`.
- **Желание «прилипнуть к низу» до жеста** оставлено поверх библиотеки: одна перегрузка `scrollToEnd()` по изменению данных, пока пользователь не прокрутил сам. Это закрывает двухстадийное открытие (кэш → сеть) и каскад «оценка → измерение», из-за которых одна разовая прокрутка вниз оставляла непрокрученную полосу.
- **`aria-live="off"` на `role="log"`.** Виртуализация монтирует/размонтирует строки при скролле; живой регион заставлял бы скринридер перечитывать историю. Новые сообщения объявляет отдельный throttled `role="status"`.
- **Сессионные якоря вынесены в модуль.** Store держит сообщения только открытого диалога, поэтому якорь живёт ровно столько же, сколько загруженный диапазон; вынесение убирает модульное состояние из компонента.

### Итерация 2 — отчёт с iOS (2026-10-15)

Симптомы с телефона (Safari, iPhone, раздел на 10 899 сообщений):

> «пока скроллишь по инерции начинает дергаться и когда уже останавливается скролл телепортирует куда-то. когда к верху подъезжаешь там начинает все дергаться 3 раза прыгать телепортироваться».

Найдены **две независимые причины**. Обе устранены.

#### Причина 1 — мой же «дозащёлкивающий» пин (мой код)

`runScrollWork` в ветке «мы у конца» сбрасывал `gestureRef`:

```ts
if (atEnd) {
  gestureRef.current = false;   // ← вот это
  followingRef.current = true;
  ...
} else if (gestureRef.current) { /* отпустить */ }
```

На iOS трекаемый `scrollOffset` отстаёт от инерции, поэтому первый же замер после флика ещё читается как «у конца» — флаг жеста сбрасывался, а на следующем замере (когда палец уже уехал) ветка отпускания не выполнялась: `gestureRef` уже `false`. В итоге `followingRef` **залипал в `true`**, и layout-эффект `scrollToEnd()` продолжал переписывать `scrollTop` прямо во время инерции. Отсюда «дёргается при костинге» и «телепорт на остановке».

Фикс:

- в ветке «у конца» `gestureRef` больше **не сбрасывается** — жест остаётся авторитетным до реального ухода от конца;
- эффект дозащёлкивания теперь заблокирован, пока жест в силе: `if (!followingRef.current || gestureRef.current) return;` — то есть он физически не может писать позицию под пальцем;
- замеры больше не читают `scrollTop`/`clientHeight`/`scrollHeight` (это форсировало layout прямо во время инерции): «у конца» считается из собственных чисел виртуализатора (`scrollOffset`, `scrollRect.height`, `getTotalSize()`);
- регрессионный тест «treats the reader's gesture as authoritative even if the coast starts at the end» воспроизводит баг: с возвращённой строкой `gestureRef.current = false` он падает.

#### Причина 2 — dev-сервер отдавал **старую версию библиотеки**

`npm install` поднял `@tanstack/react-virtual` 3.14.3 → 3.14.19 (`virtual-core` 3.17.1 → 3.19.4), но Vite оптимизирует зависимости в `apps/web/node_modules/.vite/deps` и **не заметил** изменение локфайла: кэш остался от 14 октября, а сам Vite был запущен 13 октября. Проверка маркеров подтвердила, что телефон получал старый бандл:

| Маркер | Кэш (что видел телефон) | Установлено сейчас |
|---|---|---|
| `applyContainerSize` (react-virtual ≥3.14.8) | 0 | 3 |
| `_clampedAdjustment` (virtual-core ≥3.17.5) | 0 | 9 |
| `pendingWrite` (переработка трекинга скролла) | 0 | 9 |

А именно в этих версиях лежат исправления ровно тех симптомов: «iOS-deferred scroll adjustments replaying stale deltas», «tracked scrollOffset can go negative / wedged deferred corrections», «viewport drifts when a viewport-spanning item grows», «gap at the top after an end-anchored prepend».

Что сделано: `touch apps/web/vite.config.ts` → Vite перезапустил себя и пересобрал кэш (`deps_temp_*` → `deps`), новый бандл проверен по LAN-адресу.

> **Операционный вывод.** После изменения зависимостей при уже запущенном `make dev` кэш Vite нужно принудительно сбросить (`touch apps/web/vite.config.ts` либо убрать `apps/web/node_modules/.vite`), иначе телефон/браузер будет исполнять старый бандл, а правки в исходниках при этом видны — и легко обвинить собственный код в чужих багах.

#### Причина 3 (побочно) — цепочка подгрузок у верха

Загрузчик истории был привязан к `scrollTop <= 300`. Каждая вставленная страница сдвигает `scrollTop` вверх, поэтому у верха срабатывал не один запрос, а серия — «дёргается 3 раза». Теперь условие — виртуальный диапазон (`range.startIndex <= 1`): после вставки страницы окно читателя больше не начинается со старейшего сообщения, и загрузчик разоружается до следующего подхода к верху. Одна страница на подход, как в Telegram. Тест: «loads one history page per approach to the top, not a chain».

Нюанс, который тоже закрыт: `range` равно `null`, пока скроллер не измерен, — «неизвестно» больше не трактуется как «мы наверху».

#### Что перепроверить на телефоне

1. Флик вверх из конца: инерция без рывков, на остановке позиция не меняется.
2. Подъезд к верху: одна незаметная подгрузка, без серии прыжков.
3. Возврат к концу: кнопка «к последним» появляется/исчезает, счётчик работает.
4. Открытие чата: по-прежнему ровно у низа.

Если после этого останется дрожь **во время** инерции — следующий подозреваемый `useFlushSync` (по умолчанию `true`): библиотека делает синхронный ре-рендер на каждое изменение диапазона прямо в обработчике скролла. Это уже требует замера на устройстве, менять вслепую не буду.

### Итерация 3 — настоящая причина найдена измерением (2026-10-15)

После итерации 2 симптомы остались. Тогда я перестал строить теории и снял цифры с живого рендера: подменил сеттер `scrollTop` и метод `scrollTo` у скроллера и записал все записи позиции во время настоящего скролла, а ширину колонки эмулировал как на телефоне (инъекция CSS `width: 330px`).

#### Что показал инструмент

За 8 шагов колеса (≈ −4000 px) приложение сделало **48 вызовов `scrollTo`**, собранных в 8 пачек по 4–11 штук — по одной записи на каждую **переизмеренную** строку. На iOS такие записи откладываются, пока палец и инерция живы, а затем выполняются одним пакетом сразу после остановки. Именно это — «телепорт на остановке»; а во время костинга строки стоят на *оценочных* позициях, которые были неверны — это «дёргается, пока едешь».

#### Почему оценки были неверны

`estimateMessageHeight` считала строки как `chars / 55`, где 55 — число символов в строке, снятое с **десктопной** колонки. Замер реальных пузырей на двух ширинах:

| Ширина колонки | Реальных символов в строке |
|---|---|
| 765 px (desktop) | ~52–55 |
| 315 px (телефон) | **~15–22** |

То есть на телефоне текст переносится примерно вдвое чаще, а оценка этого не знала. Измеренная ошибка на «телефонной» ширине:

| Метрика (18–31 строка) | Было | Стало |
|---|---|---|
| Средняя абсолютная ошибка | **33–36 px** | **4 px** |
| Накопленный сдвиг (сумма со знаком) | **+578 … +2320 px** | **+53 px** |
| Максимальная ошибка | **101 px** | 22 px (одна строка переноса) |
| Символов в строке | 55 (жёстко) | 22 (из реальной ширины) |

Накопленный сдвиг — это ровно та величина, которую iOS откладывает и выстреливает на остановке. Было ~600–2300 px (телепорт), стало ~50 px (лёгкое подрагивание).

#### Что изменено

- `estimateMessageHeight` принимает ширину текста; число символов в строке вычисляется из неё (`bubbleTextWidth(scrollerWidth)`).
- Ширина берётся из **трекаемого** `scrollRect.width` (без чтения DOM на пути скролла), до первого замера — из `window.innerWidth` как разумное приближение к колонке чата.
- Учтены явные переносы строк: контент рендерится с `white-space: pre-wrap`, поэтому каждый абзац переносится отдельно.
- Медиа-бокс ограничен шириной самого пузыря (на узкой колонке картинка ниже, чем на десктопе).
- Константы подобраны по реальным пузырям на двух ширинах: `BUBBLE_WIDTH_FACTOR = 0.675`, `AVG_CHAR_PX = 9`, `BUBBLE_MAX_WIDTH = 520`, `LINE_HEIGHT = 21`, вертикальная набивка 18 + 8.

Тесты, закрепляющие причину (оба падают при возврате жёстких 55 символов):

- «scales the height estimate with the column width, like the real wrap»;
- «treats explicit newlines as line breaks in the estimate».

> **Методический вывод.** Три итерации «по рассуждению» не дали результата, а инструментирование живой страницы дало причину за один заход. Для скролла нужно сразу мерить записи `scrollTop`/`scrollTo` и сверять оценки с реальными высотами, а не выводить их из кода.

### Итерация 4 — рычаги: overscan, directDomUpdates, тихая подгрузка (2026-10-15)

После итерации 3 с телефона: «где-то по 50 px перекидывает при остановке» (совпало с предсказанием: остаточная накопленная ошибка ≈ 4 px × ~12 строк) и «при дорисовке контента больше чем на экран вверх перекидывает».

Включено три изменения.

**1. `overscan: 12 → 6`.** Каждая смонтированная за пределами экрана строка — это строка, которая будет измерена, а каждое измерение — коррекция позиции. Значение взято из официального chat-примера библиотеки, а не из прежнего «ТЗ: 8–15».

**2. `directDomUpdates: true`.** Виртуализатор пишет позиции строк и высоту spacer'а прямо в DOM и делает React-коммит только при смене видимого диапазона, а не на каждое изменение офсета. На iOS именно коммит React на каждое событие скролла съедает главный поток во время инерции.

Контракт выполнен буквально (иначе библиотека оставит устаревшие inline-стили):

- строки `position: absolute; top: 0; left: 0` и **не** задают главную ось в своём стиле — `transform` теперь принадлежит библиотеке, из JSX он убран;
- spacer получает `virtualizer.containerRef` и **не** задаёт `height` — высоту пишет библиотека.

Проверено в живом браузере: 18 строк расставлены самим виртуализатором (офсеты 0 → 962, все различимы и возрастают), `transform` записан как `translate3d` (`matrix(1,0,0,1,0,90)` и далее), высота spacer'а 2841 px записана через `containerRef`, открытие ровно у низа (`distanceFromBottom: 0`).

**3. Подгрузка истории ждёт тишины.** Запрос страницы теперь только *заряжается* скроллом, а *выполняется* после паузы в 220 ms (`LOAD_SETTLE_MS`, больше библиотечного `isScrollingResetDelay` = 150 ms), с повторной попыткой, пока `isScrolling` не сбросится.

Это лечит второй симптом. Страница старой истории — это больше экрана, и если вставка приходится на живую инерцию, WebKit откладывает компенсацию скролла для prepend'а: читатель видит, как контент уезжает вниз на высоту вставки и затем возвращается, когда отложенная запись наконец применяется. При тихой загрузке компенсация применяется сразу, и вставка невидима.

Тесты: договор `directDomUpdates` закреплён (spacer от `containerRef`, строки не задают главную ось, `overscan ≤ 8`, флаг выставлен), загрузчик истории проверяется через паузу тишины.

### Итерация 5 — точные высоты до кадра + упреждающая подгрузка (2026-10-15)

После итерации 4 с телефона: ~50 px на остановке и «при дорисовке контента больше чем на экран вверх перекидывает».

Измерение на живом рендере: при подгрузке страницы строка под читателем **не двигается вообще** (`maxAnchorShiftPx = 0` на 141 замере), но библиотека делает десятки коррекций через `scrollTo` — по одной на каждую строку, чья реальная высота отличается от оценки. На iOS эти записи **откладываются**, пока палец или инерция живы, и выполняются одним пакетом, когда скролл затихает. Величина пакета = накопленная разница «оценка − факт» по строкам этой страницы; на телефоне это и есть «полстраницы».

Значит лечить надо не позицию, а **момент, когда высоты становятся известны**.

**1. Прогрев высот до кадра.** Строка уже в DOM с настоящей высотой сразу после монтирования, но библиотека узнаёт её на кадр позже — через свой `ResizeObserver`, и на iOS эта запись откладывается. Теперь `MessageList` в layout-эффекте (то есть **до отрисовки кадра**) читает `offsetHeight` смонтированных строк и кладёт их в кэш высот через `resizeItem`. Следствия:

- коррекция применяется до того, как читатель может увидеть промежуточное состояние — прыгать нечему;
- `ResizeObserver` позже находит ту же высоту, `delta === 0`, и откладывать нечего — даже если запись попадёт в запретное окно iOS, воспроизводить нечего.

Читаются только строки, которых ещё нет в кэше, поэтому в устоявшемся режиме эффект не делает ни одного DOM-чтения: закреплено тестом «stops reading the DOM once a row's height is known» (после добавления одного сообщения — ровно одно чтение, только для новой строки).

**2. Упреждающая подгрузка.** Порог загрузки истории — `HISTORY_PREFETCH_ROWS = 24` строки вместо «строго у верха» (`startIndex <= 1`). Страница уезжает в начало за экран до того, как читатель туда доедет, поэтому ничего не «дорисовывается» у него на глазах. После вставки видимое окно начинается на страницу ниже (≈50 строк), поэтому следующая грузится только после того, как он прочитает предыдущую — одна страница на подход сохраняется.

**3. Тихая подгрузка** (из итерации 4) остаётся: запрос выполняется только после 220 ms покоя, с повторной попыткой, пока `isScrolling` не сбросится.

Остаток честно: ~50 px на остановке — это ошибка оценок по строкам, которые видны **впервые**. Она неустранима без сохранения измеренных высот между визитами (`takeSnapshot()`/`initialMeasurementsCache`). Прогрев лечит разом все случаи, где высоты уже есть (открытие чата, подгрузка страницы, первое появление строки в окне при скролле — если строка успела смонтироваться до кадра).

### Итерация 6 — развести «запросить» и «вставить» (2026-10-15)

Обратная связь: «дергается и на ПК, но только в самом верху — пока не успевает подгрузить историю, а не успевает почти всегда. Порог дозагрузки надо куда больше. На телефоне во время скролла дергает, при остановке дергает, при подгрузке дергает, и в итоге может на тысячи пикселей ебашить».

Обе причины — мои, и обе в одном месте.

**1. «Не успевает» — потому что порог покоя стоял на ЗАПРОСЕ.** В итерации 4 я добавил «запрос только после 220 ms тишины». При непрерывном флинге тишины не наступает **никогда**, поэтому страница не запрашивалась вообще, пока читатель не остановится — то есть уже у самого верха. Отсюда и «не успевает примерно всегда», и одинаковое поведение на ПК и на телефоне.

**2. «На тысячи пикселей» — потому что страница ВСТАВЛЯЛАСЬ во время живого скролла.** Вставка страницы выше вьюпорта сдвигает контент под читателем; компенсирующая запись позиции на iOS откладывается до окончания инерции. Значит читатель видит сдвиг на всю высоту страницы (на телефоне это ~3000 px) ровно столько, сколько длится костинг, и потом резкий возврат.

Запрос DOM не трогает — его можно делать когда угодно. Вставка двигает позицию — её можно делать только на покое. Это два разных решения, и теперь они разведены.

**Реализация.**

- `loadMoreMessages(conversationId, { postpone: true })` — запрос трогает только буфер (`pendingOlderPages` в сторе), не `messages`. Курсор следующей страницы берётся от самого старого сообщения буфера, иначе та же страница запрашивалась бы вечно. Буфер ограничен ~100 сообщениями (две страницы).
- `flushPendingOlderMessages(conversationId)` — вставка буфера в `messages`. Вызывается **только на покое** (тишина 220 ms или `isScrolling === false`) и никогда во время костинга; если читатель успел сменить диалог, страница не вставляется в чужой список.
- `HISTORY_PREFETCH_ROWS = 24 → 100`: запас хода — несколько экранов, плюс до двух страниц в буфере сверху. Теперь страница приезжает заранее, а не «уже у верха».
- Запрос выполняется из обработчика скролла и из layout-эффекта без всякого гейта (только cooldown 500 ms), вставка — из таймера покоя и из layout-эффекта при `!isScrolling`.
- Вставка происходит до кадра и с уже прогретыми точными высотами (итерация 5), поэтому сдвига не видно вообще.

Тесты: стор — `postpone` не вставляет страницу, курсор берётся из буфера, вставка очищает буфер, чужая страница не вставляется после смены диалога; список — «never inserts a buffered page while the coast is live» (пока `isScrolling` — вставки нет; как только покой — вставка) и запрос уходит с `{ postpone: true }`.

Попутно почищена протечка в тестах стора: `isLoadingMore`/`hasMoreMessages` не сбрасывались между тестами и влияли на следующие.

### Итерация 7 — первоисточник найден, высоты измеряются точно (2026-10-15)

Поиск по проблеме дал точный ответ, а не догадку.

**Это известный баг WebKit 187449 «Cannot set scrollTop during momentum scroll phase»** (<https://bugs.webkit.org/show_bug.cgi?id=187449>):

> «In most desktop browsers, when setting scrollTop during scroll, scrollTop is set and scrolling continues at the same momentum… **Unfortunately, all major browsers on iOS seem to prevent setting scrollTop during the momentum scroll phase, resulting in jitteriness**.»

Именно поэтому библиотека не пишет коррекции во время инерции, а **откладывает** их и выполняет одной записью, когда скролл затихает (это прямо описано в её документации: «On iOS WebKit, scroll-position writes are deferred… The cumulative delta is flushed in a single write once the scroll settles»). Размер этой единственной записи = суммарная разница «оценка − факт» по строкам, которые проехали во время жеста. Это и есть «дергает при инерции и телепортирует при остановке».

Ту же проблему независимо обходят все: Flarum (перешёл на `window.scrollTo`, потому что `scrollTop` молча игнорируется), Expensify (гасит инерцию, пишет позицию, включает обратно), Popmotion (`-webkit-overflow-scrolling: auto` → запись → `touch`), virtua (компенсирует сдвиг CSS-смещением вместо записи в скролл). Apple починила это в WebKit main только в 2026 (PR #61534), а TanStack закрыл свой issue #884 со словами «на iOS 27 запись `scrollTop` больше не останавливает инерцию».

Вывод: **единственный способ не получить отложенную пачку — не иметь коррекций.** То есть высоты строк должны быть известны **до** того, как строка впервые отрисована.

**Проверка точности.** Измерил реальную строку и её внеэкранную копию:

| Что сравнивалось | Результат |
|---|---|
| `chromeDiff` (набивка/рамка/мета пузыря) | **0 px** на всех строках |
| `contentDiff` (высота текста), пересборка разметки руками | 4…13 px ошибки |
| `contentDiff`, **клонирование настоящей строки** в том же контейнере | **0 px на 16 из 16 строк** |

Разница в последней строке таблицы — ключ: если измерять не «похожую» разметку, а клон реальной строки, вставленный внутрь мессенджерного лейаута (тот же шрифт, та же тема, та же ширина), высота совпадает **пиксель в пиксель**. Ошибка 4–13 px у ручной пересборки — это её собственный дефект, а не свойство метода.

**Реализация** (`core/offscreenMeasure.ts` + `MessageList`):

1. `BubbleMeasurer` держит скрытый хост внутри `.chat-messages-area` и шаблон — клон настоящей текстовой строки. Все пробы вставляются за один проход, высоты читаются одним проходом (одна раскладка на пачку).
2. На изменение данных (страница приехала на покое, чат открылся) `MessageList` измеряет **все** сообщения, которых ещё нет в кэше высот, и кладёт точный размер через `resizeItem`.
3. Результат: к моменту, когда строка впервые монтируется, её высота уже точна → `delta === 0` → **коррекции не возникает вовсе** → откладывать нечего → нет ни дёрганья при инерции, ни телепорта на остановке.
4. Прогрев не выполняется во время скролла (`isScrolling`) — иначе записи снова попадут в запретное окно; таймер покоя повторяет попытку.
5. Старый прогрев по `offsetHeight` смонтированных строк оставлен страховкой для строк, которые нельзя воспроизвести (медиа, карточки-шеры, rich text) — они по-прежнему живут на оценке.

Ограничения честно: строки с медиа/шерами/цитатами/эмодзи-токенами по-прежнему оцениваются (их разметку воспроизводить опасно), и высота, изменившаяся позже (догрузилась картинка, отредактировали сообщение), корректируется как раньше.

### Итерация 8 — подтверждено на iPhone (2026-10-15)

> «теперь реально как будто нормальный мессенджер. даже на айфоне почти не прыгает… иногда при подгрузке чисто на пикселей 20 дергает мб а в целом заебись».

Итог: механизм подтверждён на устройстве. Что дало результат, по убыванию вклада:

1. **Точные высоты до первой отрисовки строки** (`core/offscreenMeasure.ts`) — коррекций не возникает, значит iOS нечего откладывать и нечем «выстреливать». Это была основная причина.
2. **Вставка страницы только на покое** (буфер `postpone`/`flushPendingOlderMessages` в сторе) — вставка выше вьюпорта больше не попадает в окно инерции.
3. **Запрос истории задолго до верха** (порог 100 строк) + развязка «запросить» и «вставить» — история больше не «не успевает».
4. `directDomUpdates` — React не коммитит на каждое изменение offset'а.
5. `overscan: 6` вместо 12.

Остаток: ~20 px (ровно одна строка текста) при подгрузке — это строка, которая **не** измеряется вне экрана и живёт на оценке: медиа, карточки-шеры, цитаты, ссылки (превью подгружается асинхронно) или эмодзи-токены (их рендер не совпадает с `textContent`). Закрывается сохранением измеренных высот между визитами — тогда и эти строки точны со второго прохода.

### Что осталось проверить (не выполнено)

Динамические сценарии требуют видимого окна браузера или устройства. В текущей среде десктопное окно браузера невидимо: `document.visibilityState === "hidden"`, `requestAnimationFrame` не тикает, scroll-события не доставляются, `browser.screenshot` отказывает с «Screenshot needs a visible tab». Прятать это не нужно — поэтому по фазам 5–6 ничего не заявлено.

Осталось:

1. Пиксельная устойчивость prepend'а: одно и то же сообщение должно остаться на той же экранной координате после подгрузки страницы (проверять с живым кадром).
2. Пилюля «N новых» при реальном входящем сообщении по WebSocket, когда читатель в истории.
3. iOS Safari и Android Chrome: momentum scroll, экранная клавиатура, URL-bar, ориентация, `overscroll-behavior`.
4. VoiceOver/TalkBack/NVDA и клавиатурная навигация по виртуализированному списку.
5. Профиль на 10 000 сообщений (сейчас в сиде ~200): DOM count, commits, dropped frames, память, при необходимости — оценка `directDomUpdates`.

## 1. Цель

Сделать длинную историю Messenger плавной и предсказуемой на desktop, iOS Safari и
Android Chrome: в том числе при чтении 10 000+ сообщений, догрузке старой истории,
получении новых сообщений, загрузке медиа, редактировании сообщения, смене диалога
и открытой экранной клавиатуре.

Главная гарантия: **изменение данных выше видимой области не должно перемещать
сообщение, которое пользователь сейчас читает**. Новые входящие сообщения не должны
выдёргивать человека из истории. Размер DOM должен зависеть от viewport, а не от
числа когда-либо загруженных сообщений.

Это план именно списка сообщений и его взаимодействия с историей. Переписывание
композера, изменение модели шифрования и полная переделка Messenger сюда не входят.
Мобильную клавиатуру проверяем как интеграционный сценарий, но меняем её отдельно.

| Решение | Выбор |
|---|---|
| Виртуализатор | **TanStack Virtual** |

## 3. Результаты исследования

### 3.1 Что подтверждено первичными источниками

- TanStack Virtual документирует чатовый режим: `anchorTo: 'end'`, стабильные ключи,
  `followOnAppend`, порог нахождения у конца и измерение динамических строк. Это
  прямо покрывает prepend старых сообщений и append новых без переворота списка и
  ручного `scrollTop += delta`.
- В официальном блоге TanStack описаны отдельные исправления производительности,
  динамической высоты и momentum scroll на iOS. Это сильная причина использовать
  актуальный проверенный релиз библиотеки, а не копировать старый самодельный
  движок.
- Slack описывает ленивую загрузку истории страницами; размер страницы выбирался
  экспериментально. Их исторический размер 42 — не магическая константа для Gomo6.
  В проекте уже принят размер около 50 сообщений, его следует оставить до замеров.
- Discord описывает измеренные оптимизации мобильных списков и нативного чата.
  Это подтверждает ценность измерений и ограничения живых представлений, но не
  доказывает конкретную реализацию их web-клиента.
- Virtuoso `Message List` — отдельный коммерческий продукт. Обычный
  `react-virtuoso` — другой пакет. С учётом выбора пользователя и уже имеющегося
  TanStack переход на коммерческий пакет не нужен.
- Веб-платформа может сама выполнять часть прокрутки на compositor thread. Поэтому
  одних FPS или субъективного ощущения недостаточно: нужно смотреть dropped frames,
  main-thread traces, layout shifts и реальную позицию якоря.

## 4. Принципы реализации

1. **Один владелец scroll physics.** TanStack Virtual отвечает за end anchoring,
   динамические измерения и follow. Не добавлять параллельно ручные поправки
   `scrollTop`, `scrollHeight`-дельты и независимый browser-anchor fallback без
   доказанного бага и отдельного теста.
2. **Нативный scroll-контейнер.** Сохранить обычный порядок сообщений и браузерный
   touch/trackpad scrolling. Не использовать `column-reverse`, `scaleY(-1)` и
   `preventDefault` на каждом touch/scroll событии.
3. **Идентичность по данным, не по позиции.** Ключ строки — `messageKey(message)`;
   никогда не индекс массива. Это необходимо для optimistic → server замены и
   prepend страниц.
4. **Сначала корректность, затем fast path.** Не включать прямые DOM-обновления,
   ручной pooling строк или массовые CSS/compositor-трюки без trace, показывающего
   реальное узкое место.
5. **Виртуализация DOM не равна выгрузке данных.** Не удалять историю из памяти
   только ради виртуализации. Сначала измерить 10 000 сообщений; eviction/страничный
   LRU — отдельная оптимизация только при подтверждённой проблеме памяти.
6. **Реальное устройство — обязательная проверка.** jsdom не моделирует высоту,
   iOS momentum scroll, экранную клавиатуру или реальный scroll anchoring.

## 5. Целевая структура

```text
MessengerView
  └─ ChatView                         состояние выбранного диалога/композера
       ├─ ChatHeader / pinned banner
       ├─ MessageList                  viewport + TanStack Virtual
       │    ├─ MessageRow              дата, группировка, Bubble
       │    └─ ListScrollController    follow, якорь, новые, restore
       └─ MessageComposer

messengerStore                        сообщения, страницы, realtime, receipts, cache
  └─ messageModel                     порядок, стабильные ключи, merge/dedupe
```

Это логическое разделение ответственности, не требование создать большой новый
framework. Предпочтительно оставить TanStack-конфигурацию рядом с `MessageList`, а
поведение прокрутки выделить в небольшой хук только если это уменьшает число
взаимосвязанных эффектов и облегчает тестирование.

### 5.1 Store и состояние на диалог

История должна оставаться доступной при переключении между недавно открытыми
диалогами в рамках сессии. Одного сохранённого `scrollTop` недостаточно: после
изменения высот он может указывать на другое место, а текущий IndexedDB-кэш в 50
сообщений может не содержать старый видимый якорь.

Ввести или сохранить по `conversationId` минимальное состояние сессии:

- загруженный упорядоченный диапазон сообщений;
- старейший cursor, `hasMore` и статус запроса страницы;
- последняя сохранённая позиция (ключ видимого сообщения + пиксельное смещение);
- состояние «пользователь был у конца» для возврата в диалог.

Интегрировать постепенно с текущим store и его поколениями запросов. Не менять
REST/WS-контракт без необходимости. Вопрос долговременного кэша за пределами сессии
решать отдельно; не хранить расшифрованные «Заметки» в IndexedDB.

### 5.2 Модель виртуальной строки

- Список получает хронологический массив или фильтрованное представление «Заметок».
- `getItemKey` возвращает канонический `messageKey()`.
- Высота измеряется по реальному DOM через `measureElement`; `estimateSize` служит
  только первичной оценкой до первого измерения.
- Группировка автора и разделитель даты рассчитываются относительно соседних
  сообщений в полном загруженном диапазоне, а не относительно соседних DOM-узлов
  видимого окна.
- Индикатор начала истории/загрузки не должен менять высоту над якорем без
  измерения и согласованной коррекции виртуализатора.

## 6. Контракт поведения прокрутки

### Открытие диалога

1. Если для диалога есть позиция в сессии и соответствующий диапазон — восстановить
   якорь и его смещение.
2. Иначе показать последнюю страницу и после регистрации viewport один раз перейти
   к последнему сообщению.
3. Кэш и сеть не должны вызывать последовательное мерцание `пусто → список → пусто
   → список`. При необходимости показывать loader поверх данных, а не размонтировать
   список между источниками.
4. Асинхронные измерения строк и медиа не должны сбивать первоначальный end anchor.

### Догрузка вверх

1. По виртуальному диапазону заранее определить приближение к старейшему сообщению.
2. Выполнить не более одного запроса старой страницы на диалог; использовать
   существующий cursor `before` и `loadMoreMessages()`.
3. Добавить страницу через существующий `prependOlder()`.
4. `anchorTo: 'end'` и стабильные ключи должны сохранить то же сообщение в том же
   месте. Не делать ручную компенсацию через разницу `scrollHeight`.
5. По завершении истории показать корректное состояние конца списка; не запускать
   повторные пустые запросы.

### Новые сообщения

- Виртуализатор должен следовать за append только если пользователь был у конца до
  обновления.
- Порог `scrollEndThreshold` выбрать тестированием. Не принимать 80 px за истину:
  прошлые проблемы Messenger показывали, что широкий порог может ощущаться как
  принудительное притягивание вниз. Начать с малого порога, затем проверить на
  разной высоте окна и плотности сообщений.
- Для входящих сообщений использовать автоматическое/мгновенное удержание у конца,
  а не долгую smooth-анимацию на каждое событие.
- Если пользователь читает историю, сохранить якорь и показать кнопку/счётчик
  новых сообщений. Счётчик сбрасывается при явном переходе к последнему сообщению.
- Отправка своего сообщения — отдельное пользовательское намерение; его UX надо
  проверить отдельно от поведения фоновых входящих событий.

### Изменение высот

- Изображения и видео заранее резервируют место по известным метаданным, cache ratio
  или стабильной fallback-пропорции.
- По завершении загрузки, изменении ширины viewport, edit, раскрытии превью и
  реакции виртуализатор измеряет затронутые строки.
- Если изменилась строка выше видимого якоря, сохранять позицию по правилам
  виртуализатора. Если пользователь у конца, end anchoring должен удержать конец.
- Не менять одновременно estimate, CSS padding, bubble compactness и размеры медиа
  серией независимых layout-effect без измерений и trace.

### Read receipts и доступность

- Интегрировать фактически видимый диапазон с существующей очередью read receipts.
  Overscan не считается прочитанным. При переключении вкладки/диалога не отправлять
  receipt для невидимого контента.
- Проверить актуальность комментариев о видимости в `ChatView.tsx` и `messengerStore.ts`:
  наличие очереди в store само по себе не означает, что список сообщает видимые строки.
- Не заставлять screen reader заново зачитывать целую виртуализированную историю
  при каждом изменении окна. Проверить семантику log/list и точечные объявления новых
  сообщений с VoiceOver, TalkBack и NVDA.
- Не подставлять неверные `aria-posinset`/`aria-setsize`. Если серверный общий размер
  неизвестен, не выдавать размер загруженного окна за полный размер истории.

## 7. План фаз

### Фаза 0 — зафиксировать baseline и тестовый корпус

**Задачи**

- Записать поведение текущей ветки и проверить фактические API/типы установленного
  TanStack Virtual.
- Подготовить fixture из 10 000 смешанных сообщений: короткий/длинный текст,
  групповые сообщения, даты, ответы, вложения, share/gift, удалённые сообщения.
- На desktop и телефоне записать исходную трассу: открытие, быстрый scroll вверх/
  вниз, загрузка страницы, приход сообщения, позднее медиа.
- Отдельно проверить «Заметки» с большим набором и фильтрами.

**Gate:** поведение и точки измерения воспроизводимы; цифры не придуманы по одному
ощущению на машине разработчика.

### Фаза 1 — обновить и изолированно проверить виртуализатор

**Задачи**

- Обновить lockfile до актуального стабильного `@tanstack/react-virtual` в пределах
  существующего диапазона и зафиксировать разрешённый `virtual-core`.
- Проверить наличие `anchorTo`, `followOnAppend`, `scrollEndThreshold`,
  `scrollToEnd()` и API измерения в именно установленной версии.
- Запустить текущие frontend-тесты и typecheck; сверить изменения release notes по
  iOS deferred scroll writes и динамическим высотам.
- Не переходить на Virtuoso и не включать пока прямые DOM-обновления.

**Gate:** чистая установка по lockfile даёт те же версии; тесты и typecheck зелёные.

### Фаза 2 — виртуализировать `MessageList`

**Файлы:** `MessageList.tsx`, тесты `MessageList.test.tsx` и при необходимости
небольшой файл модели строк.

**Задачи**

- Заменить полный `.map()` на virtual range.
- Подключить стабильный `messageKey()` и измерение динамических строк.
- Сохранить обычный порядок, роли/доступность, дату, sender grouping и API
  `renderMessage` насколько возможно.
- Проверить `messagesOverride` для папок «Заметок».
- Сделать тесты на windowed rendering, стабильные ключи и boundary rows. Не мокировать
  scroll physics так, будто jsdom может её подтвердить.

**Gate:** количество DOM-строк зависит от viewport/overscan, а не от 10 000 записей;
контент видимых строк совпадает с обычным списком.

### Фаза 3 — скролл-контракт и история

**Файлы:** `MessageList.tsx`, небольшой controller/hook при необходимости,
`messengerStore.ts`, тесты model/store.

**Задачи**

- Включить end anchoring и условный follow-on-append.
- Убрать только ту самодельную прокрутку, которая реально существует в текущем
  исходнике; не удалять функции по устаревшему документу.
- Подключить предзагрузку старой страницы к диапазону virtualizer с дедупликацией
  триггера и сохранением текущего cursor-поведения.
- Добавить «Новые сообщения» и переход к последнему сообщению.
- Сохранить историю и якорь по `conversationId` при смене диалога в пределах сессии.
- Проверить отправку собственного сообщения отдельно от append входящего WS-события.

**Gate:** prepend не сдвигает якорь; входящие не уводят из истории; при нахождении
у конца новые сообщения остаются видимыми.

### Фаза 4 — медиа, строки и receipts

**Файлы:** `MessageContent.tsx`, `MessageMediaMosaic.tsx`, `attachmentMedia.ts`,
`attachmentRatioCache.ts`, `ChatView.tsx`, `messengerStore.ts` — только по найденным
проблемам.

**Задачи**

- Проверить резервирование высоты и повторные измерения всех типов вложений.
- Проверить, не пересоздаёт ли каждый append весь список или тяжёлые производные
  данные в `ChatView`.
- Подключить receipts к реально видимым строкам; вылечить безусловные store writes,
  если trace показывает лишние перерисовки.
- Сохранить ответы, закрепление, действия над строкой, share/gift и notes controls.

**Gate:** после загрузки картинки, редактирования и ресайза сохраняется ожидаемый
якорь; только видимое может быть отмечено прочитанным.

### Фаза 5 — мобильная стабилизация и доступность

**Задачи**

- Проверить iOS Safari и Android Chrome с momentum scroll, открытой/закрытой клавиатурой,
  URL bar resize, safe area и изменением ориентации.
- Оставить `mobileKeyboard.ts` отдельной подсистемой. Исправлять его только отдельным
  изменением с собственными регрессионными тестами.
- Проверить scroll chaining и `overscroll-behavior` на целевых WebKit-версиях, не
  полагаясь на это свойство для правильности якоря.
- Проверить VoiceOver, TalkBack, NVDA/клавиатуру; отдельное объявление новых сообщений
  не должно дублировать каждый виртуальный remount.

**Gate:** минимум iPhone/iOS Safari и Android Chrome проходят ручной сценарий; headless
WebKit не считается заменой реального устройства.

### Фаза 6 — профиль, настройка и безопасный rollout

**Задачи**

- Повторить baseline-файлы на том же тестовом корпусе и устройствах.
- Сравнить DOM count, React commits, layout/measure work, dropped frames, memory и
  input responsiveness.
- Подбирать overscan и страницу истории по реальным traces/латентности. Начать с
  официального chat example TanStack как ориентира, но не копировать его числа
  вслепую.
- Только если trace докажет React range-render bottleneck — отдельно проверить
  `directDomUpdates`; проверить stacking contexts, fixed/popover descendants и
  поведение с медиа.
- Удалить тесты/комментарии, которые утверждают старый контракт, но не удалять
  unrelated CSS/компоненты «заодно».

**Gate:** регрессий в сценариях и браузерах нет; измеренная прокрутка не хуже baseline,
и проблема 10 000 строк устранена по критериям ниже.

## 8. Тестовая матрица

### Unit/model/store

- `messageKey()` сохраняет место при optimistic → server замене.
- prepend с пересечением страниц дедуплицируется и не переставляет совпавшие строки.
- concurrent load-more ограничен одним запросом на диалог; устаревший ответ не
  перетирает выбранный чат.
- `hasMore` корректно проходит короткую, полную и пустую последнюю страницу.
- группировка и даты корректны на границах загруженных страниц и virtual window.
- переключение диалога не путает сообщения, cursor, receipt и сохранённый anchor.

### Browser/E2E

- open у конца, prepend на середине истории, быстрый scroll вверх/вниз;
- incoming append у конца и в середине истории;
- image/video load и ratio-cache mutation выше, внутри и ниже viewport;
- resize окна, смена ориентации, клавиатура при фокусе редактора;
- переход к quoted/replied message, pinned, поиск/переход, edit/delete;
- notes: 10k+ записей, folder filter, pinned area, смена фильтра;
- проверка отсутствия пустого просвета при догрузке и при изменении измерений.

Автотесты с layout запускаются в реальном браузере. Устройство нужно для проверки
touch inertia, iOS WebKit и поведения клавиатуры.

## 9. Критерии готовности

1. Для 10 000 загруженных сообщений число смонтированных message rows ограничено
   видимым диапазоном плюс выбранный overscan; оно не растёт линейно с историей.
2. При prepend то же сообщение остаётся на той же визуальной координате после
   завершения layout/measurement.
3. При append пользователь у конца видит последнее сообщение; пользователь в истории
   остаётся на своём якоре и получает доступный переход к новым.
4. Позднее медиа и динамическое изменение строки не создают повторяющиеся скачки.
5. После смены и возврата в диалог восстанавливается anchor, если диапазон сохранён.
6. Нет дублирующих запросов старой страницы и повторного рендера всего чата на каждом
   scroll-событии.
7. Desktop, iOS Safari и Android Chrome проверены; нет регрессий ввода и клавиатуры.
8. Performance trace показывает конкретное улучшение относительно baseline; средний
   FPS не используется как единственное доказательство плавности.

Целевые пороги по кадрам и памяти зафиксировать после Фазы 0 на целевых устройствах.
Для 60 Hz ориентир кадра — 16,7 ms, для 120 Hz — 8,3 ms; не обещать один и тот же
результат на каждом устройстве и не скрывать пропуски усреднённым FPS.

## 10. Риски и защита от регрессий

| Риск | Защита |
|---|---|
| TanStack и ручная компенсация одновременно меняют scroll offset | Один владелец коррекции; ручной fallback только с reproducer и тестом |
| Неверные ключи при prepend/optimistic echo | Использовать `messageKey()`, тестировать ID до/после ответа сервера |
| Оценочная высота далека от фактической | Представительные estimates, измерение DOM, резервирование размеров медиа |
| Якорь восстановлен, но его сообщения нет в памяти | Хранить загруженные страницы диалога на время сессии; fallback описать явно |
| iOS ведёт себя иначе, чем Chromium | Настоящие устройства; не полагаться на scroll anchoring как на контракт |
| Overscan маскирует ошибку receipts | Read receipts считать только по реальной видимости, не по смонтированным строкам |
| Переписывание захватывает композер и клавиатуру | Скролл и keyboard changes — отдельные фазы/изменения |
| Включение direct DOM creates stacking bugs | Только после доказанного профилем выигрыша и E2E проверки overlay/fixed элементов |
| «Заметки» перестают находить далёкие закрепления | Оставить текущую полную модель заметок, виртуализировать только представление |
