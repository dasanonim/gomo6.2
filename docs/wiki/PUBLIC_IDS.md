# Дизайн-док: публичные номера (`public_id`) вместо UUID в ссылках

> Статус: **фазы 1–5 сделаны и проверены; фаза 6 (143) убрала резерв и рынок**
> Версия: 1.5 (2026-10-25)
> Решения: номера **последовательные, per-table, с 1**; резерва полос нет;
> сервисная строка — NULL; леджер трансферов и assign-хендлер удалены

## 1. Цель

Убрать UUID из URL. Сейчас ссылки вида `profile/45166086-…/wall/545dd9ec-…`,
`thread/20d1f4de-…` — нечитаемые и некрасивые. Целевое состояние: короткий числовой
номер в ссылке, в стиле форумов.

```
/profile/42              ← человек (линия users, с 1)
/thread/315              ← тема (линия threads, с 1)
/profile/42/wall/1337    ← пост на стене (линия profile_wall_posts, с 1)
```

**Вне объёма:** мессенджер, чаты GomoSub, борды/эмодзи (у них уже slug), модерация
(внутренние страницы остаются на UUID), federation (там `:identifier` / `:slug`).

## 2. Решения

### 2.1 Что решили

| Решение | Почему |
|---|---|
| **UUID остаётся PK**, `public_id` — отдельная колонка-алиас | Смена PK ломает S3-ключи (`<userID>/…`), ownership-проверки, 134 миграции и все FK. См. §2.3 |
| **Последовательные** номера, не случайные | Осознанный выбор ради форумной эстетики: номер по порядку регистрации |
| **Свой sequence на таблицу** | Общий счётчик съедался бы постами и убил бы «низкий номер = старичок» на линии юзеров. Модель — как у lolz: id юзера = порядок регистрации |
| **Порядок = `created_at`** | Backfill `ORDER BY created_at, id`: кто зарегался раньше — тот получает меньший номер |
| **Никакого резерва: все линии с 1** | Резервные полосы (users с 10, threads со 100) и рынок номеров убраны миграцией 143 — на старте они давали уродские первые ссылки (#10, #100) ради престижа, которого нет без юзеров |
| **Служебные строки — NULL, не номер** | Сервисный аккаунт `__system__` держит NULL (колонка nullable с 143). Резолвер принимает только положительные десятичные, фронт падает в UUID-фолбэк |
| **`profiles`-вью обновляется вместе с `users`** | `profiles` — это VIEW над `users`; без public_id в его колонках номер не виден в джойнах (`friends.go:607,660`, `profiles/username.go:9`) |

### 2.2 Что решили НЕ делать

| Отклонено | Почему |
|---|---|
| 7-значные номера | Убивают «низкий номер = старичок». Плюс `MAX(id)` рос бы по постам, а не по юзерам |
| Рынок номеров (выдача/перепродажа, леджер) | Убран в 143: механика коллекционирования без юзеров — мёртвый код и ломаные ссылки при свопе. Вернуть только осознанным продуктовым решением |
| Таблица-реестр резерва (`public_id_reserves`) | Не нужна: резерва больше нет, все линии нумеруются с 1 |
| `/u/:username` вместо UUID | `username` меняется (`profiles.go:648`, `ErrUsernameTaken`) — понадобились бы редиректы и история. `public_id` иммутабелен и не зависит от смены ника |
| `GENERATED … AS IDENTITY` | Нельзя чеканить явным INSERT без `OVERRIDING SYSTEM VALUE`, и неудобно переназначать — а выдача номера = обычный `UPDATE public_id` |

### 2.3 Почему последовательные номера тут допустимы (аудит утечек)

Проверено по коду, а не «на глаз»:

- **Медиа защищено видимостью, а не только владением.** Приватные бакеты исключены из
  прямого проксирования в Garage (`Caddyfile:144-147`, `270-273`) и всегда идут через
  бэкенд: `uploads` требует авторизации, `wall` — авторизация + `privacy.WallAttachmentAccess`
  (предикат видимости стены, а не загрузчика) с 403 иначе (`routes.go:863-906`,
  `privacy.go:176-210`). Публичные бакеты (`avatars`, `content`, …) анонимны by design.
- **Ключи объектов неймспейсятся UUID'ом** (`<uploaderID>/avatar_<ts>.jpg`,
  `upload.go:281-283`; приватный бакет `wall/<authorID>/<key>`, `wall/document.go:356`).
  Значит даже полностью перечисляемый числовой `public_id` не даёт собрать URL медиа —
  в ключе всё равно неугадываемый UUID.
- **База юзеров уже перечисляема by design.** `GET /profiles` — на guest-группе
  (`routes.go:428`), 100 строк на страницу, `ORDER BY created_at DESC`; email режется для
  не-владельца (`profiles.go:316`), приватным режутся аватар/био/статы, но `username`,
  `display_name`, `avatar_url`, `created_at`, `domain` видны всем.

**Итог:** последовательные номера не открывают контент. Остаётся метадата: `MAX(public_id)`
как счётчик объектов, дырки как след модерации, 404-vs-403 как oracle существования
приватного объекта. Для этого проекта принято как приемлемая цена за эстетику.

## 3. Нумерация

| Таблица | С | Почему так |
|---|---|---|
| `users` | **1** | Первый зарегавшийся — №1. Служебных номеров нет: сервисный аккаунт держит NULL (§5) |
| `threads` | **1** | Первый тред — №1. Дырки от жёстких удалений (`107`) — норма, как везде |
| `profile_wall_posts` | **1** | Номер служебный: URL всё равно скоупится владельцем стены |
| `posts` | **не планируется** | Посты в тредах, судя по продукту, вероятно исчезнут — линия деприоритизирована. Номер понадобится, только если посты останутся |

Миграция 143 — one-shot перенумерация: сдвинуть номера задним числом = сломать уже
разошедшиеся ссылки. Сделано до запуска, когда ссылок в дикой природе почти не было.

## 4. Инварианты (не ломать)

1. `public_id` **никогда** не участвует в авторизации и ownership. Все IDOR-предикаты
   остаются на UUID (`user_id` / `author_id`). `public_id` — только резолв и отображение.
2. Клиентские write-пути не могут задать `public_id`: он не должен попадать ни в
   `WritableColumns` (`crudengine/table_registry.go`), ни в typed update-структуры.
   Назначение номера — только админский путь (фаза 5).
3. `public_id` уникален и никогда не переиспользуется.
4. Старые UUID-ссылки работают **вечно**: параметр маршрута принимает и UUID, и цифры.
   Никаких редиректов и таблиц истории для этого не нужно.

## 5. Фаза 1 — сделано

**Файлы**

- `apps/backend-go/migrations/128_public_ids.sql`
- `apps/backend-go/internal/database/public_ids_migration_test.go`

**Что делает миграция**

- `public_id BIGINT NOT NULL` + `UNIQUE`-индекс на `users`, `threads`, `profile_wall_posts`,
  у каждой линии свой sequence с нужной базой.
- Backfill `ROW_NUMBER() OVER (ORDER BY created_at, id)` от базы вверх.
- `setval(MAX)` **только при непустой таблице** — на пустой sequence остаётся на своей
  базе, поэтому первый insert попадает ровно на базу, а не на базу+1.
- Пересборка `profiles`-вью (27 колонок из `091` + `public_id`).

## 6. Фаза 2 — бэкенд-резолв

**Статус: сделано полностью** (волна 1 — резолв и основные чтения, волна 2 — все
payload'ы, из которых фронт строит ссылки).

**Совместимость:** параметр маршрута принимает и UUID, и цифры. `internal/publicid`

по-прежнему принимают только UUID**.

Контракты, которые важно знать:
- `/threads/:id` для мусора отвечает **400** (как и раньше — `ParseParamStrict`);
- `/profiles/:id` для мусора отвечает **404** (новое; раньше был 500 на uuid-касте);
- фильтры `?public_id=eq.<мусор>` → 404 (люди) / 400 (темы), а не 500.

### 6.2 Сделано (волна 2) — payload'ы, из которых фронт строит ссылки

| Payload | Что добавлено |
|---|---|
| Поиск | `u.public_id` (люди), `t.public_id` (темы), `t.public_id AS thread_public_id` (посты ищутся, но ссылка ведёт на тред) — `handlers/search.go` |
| «Mr. рандомность» | `public_id`, `wall_user_public_id`, `post_public_id` у элементов пула — `handlers/random.go` |
| Избранное | `public_id` + `user_public_id` в обеих ветвях UNION и в скане — `handlers/favorites.go` |
| История | то же — `handlers/history.go` |
| Лайкнувшие | `u.public_id` в списке лайков треда — `handlers/likes.go`; `u.public_id` в recent-likers RPC — `rpc/rpc_likes.go` |
| Уведомления | `related_user_public_id`, `related_thread_public_id`, `related_wall_post_public_id`, `related_wall_user_public_id` (второй проход по PK) — `handlers/notifications.go`, `models.Notification` |
| Лента | `public_id`, `user_public_id`, `author.public_id` — второй проход по PK в `handlers/feed.go` |

Два решения по реализации:

- **Лента и уведомления резолвят номера вторым проходом**, а не JOIN'ом в основной
  запрос. Причина: `get_user_feed` — единственный источник правды по порядку
  (score-сортировка), и оборачивать её в JOIN рискованно: план может переставить
  строки. Второй проход — один `UNION`-запрос по PK, порядок не трогается; на сбое
  логируем и отдаём ответ без номеров (фронт падает в UUID-фолбэк).
- **`get_user_feed` не менялась** — миграция не понадобилась.

## 7. Фаза 3 — фронт

**Статус: сделано** (ссылки + резолв параметра маршрута).

### 7.1 Линк-билдеры

`src/utils/entityUrl.ts`: `isPublicId`, `entityParam`, `profileUrl`, `threadUrl`,
`wallPostUrl`. Номер предпочитается, UUID — фолбэк; при отсутствии обоих возвращается
пустая строка, а не полусобранный URL.

`?? id` — это страховка на время раскатки: React Query-кэш может ещё держать ответы,
полученные до появления `public_id`, и пропавший номер должен деградировать в
UUID-ссылку, а не в `/profile/undefined`.

Переведены: карточки тредов (`ThreadCard`, `FeedThreadCard`, `GomoThreadCard`,
`CompactThreadList`, `Board`, шэр-URL треда, `CreateThread`/`CreateGomoThread`),
`ShareCard`, поиск (люди, темы, попадания по постам — через номер треда), `MrRandom`,
дропдаун поиска в шапке, авторы комментариев (`ThreadCommentTree`, `WallCommentNode`),
друзья и заявки в друзья, уведомления (`notificationLink`).

### 7.2 Резолв параметра маршрута (то, без чего числовые URL не работают)

- `useProfile` / `useThread` выбирают `public_id=eq.` или `id=eq.` по форме параметра.
- `ProfileCacheContext` резолвит числовой параметр через запрос профиля и берёт
  канонический UUID для `user_roles` и customization.
- `Profile`, `Thread`, `WallPost`, `Achievements` резолвят параметр один раз и передают
  дальше **UUID**: приватность, статус дружбы, presence-рум, опросы/подписки/история/
  редактирование, дерево комментариев, `ProfileWall`, RPC ачивок. **UUID-ссылка не делает
  лишнего запроса** — резолв включается только для числового параметра.
- Проверки владельца сравнивают резолвнутый UUID, а не сырой параметр
  (`Profile`, `ProfileTabs`, `useProfileEditing`, `Achievements`, `MobileMenu`).

### 7.3 Приёмочный скрипт

`./scripts/public-id-acceptance.sh` покрывает и поверхности под авторизацией:
регистрирует два аккаунта и проверяет, что номера есть в `GET /notifications`
(`related_user_public_id`), `GET /friends/requests` (`sender_public_id`),
`GET /friends` (`public_id`), `GET /favorites` и `GET /history`
(`public_id` + `author.public_id`) и в публичном RPC
`get_recent_thread_likers` (`public_id`). 28 проверок.

### 7.4 Что осталось на UUID-фолбэке (осознанно)

Номер протащен через пропсы туда, где он есть в payload: `UserBadge`/`PostCardHeader`
(`userPublicId` — аватары и ники в карточках тредов, стен, комментариев и в списках
лайкнувших), `MentionLink` (номер приходит вместе с профилем в упоминании),
`ProcessedContent` (`postAuthorPublicId` — ссылки «автор» в контенте), `ProfileSection`
(номер из `/auth/me`), `friendsStore` (друзья и заявки), карточки тредов
(`user_public_id`).

Осталось только то, где номера в payload нет вообще:
- мессенджер (`MessageLinkViews`, `UserInfoPanel`) — payload мессенджера не отдаёт номера;
- `GiftDetailPanel` (отправитель подарка) — payload подарков не отдаёт номера;
- страницы модерации (внутренние, вне объёма с §1).

### 7.5 Как увидеть номера локально

`public_id` появляется в API только после того, как бэкенд применит миграцию 128
(`RunMigrations` выполняется на старте). Если dev-бэкенд был запущен до неё, БД остаётся
на 127, API не отдаёт номера, и фронт честно падает в UUID-фолбэк — перезапустить
бэкенд (`make dev-stop && make dev`, либо respawn окна `backend` в tmux).

Побочный эффект резолва: страница профиля теперь делает запрос профиля до остальных
чтений (раньше все четыре шли параллельно) — один лишний round trip на холодном кэше,
сглаживается TTL-кэшем страницы.

## 8. Фаза 4 — приёмка

**Статус: сделано.** Приёмочный скрипт — `./scripts/public-id-acceptance.sh`.
Самодостаточный: поднимает бэкенд на отдельной БД (миграции применяет он сам) и на
отдельном индексе Redis, сидит фикстуры, всё проверяет и убирает за собой. Запуск не
трогает dev-стек.

Проверяет на живом стеке (все зелёные):

| Проверка |
|---|
| базы на чистой БД: `users` 10, `threads` 100, `profile_wall_posts` 1 |
| `/api/v1/profiles/<n>` == `/api/v1/profiles/<uuid>` по телу |
| `/api/v1/threads/<n>` == `/api/v1/threads/<uuid>`, номер автора в payload |
| фильтры `?public_id=eq.<n>` для людей и тем |
| пост стены: номер поста, номер владельца и номер автора в payload |
| OG-карточка по `/profile/<n>` и по UUID |
| мусор: 404 для людей, 400 для тем (и в фильтрах) |
| `public_id` в теле PUT игнорируется; PUT по числовому пути — 403 (пишут только UUID) |
| sequence продолжается после backfill |

Плюс unit/integration-тесты Go и 2475 тестов web.

### Найдено приёмкой

1. **Системный пользователь занимал #10, потом #1, потом −1, теперь NULL.**
   История граблей в трёх актах: сначала `SeedDevDashboardApp` съедал первый
   органический номер, потом его посадили на `#1`, потом на неадресуемый sentinel
   **−1**. Миграция 143 закрыла вопрос по-человечески: у сервисной строки
   `public_id = NULL`, резолвер принимает только положительные десятичные,
   фронт падает в UUID-фолбэк. Фронт по-прежнему обязан игнорировать
   неположительные номера (`entityParam` это делает, см. §7.1) — защита от
   кривых данных, а не от живых сентинелов.
2. **Мусор в `/profiles/:id` давал 500** (uuid-каст в Postgres). Строгий резолвер
   отвечает 404; `/threads/:id` сохраняет свой 400.
3. **`/auth/me` не отдавал номер**, из-за чего свои ссылки (шапка, меню) собирались по
   UUID. Добавлен `public_id` в payload и в кэш профиля.

## 9. Фаза 5 — выдача и трансферы (рынок): УДАЛЕНО

Механика выдачи/перепродажи номеров убрана миграцией 143 вместе с хендлером
`handlers.PublicIDHandler.AssignPublicID`, таблицей `public_id_transfers` и
фазой-5 в acceptance-скрипте (теперь там проверка, что маршрут отдаёт 404).
Номера выдаются один раз из sequence с 1 и никогда не двигаются. Вернуть рынок —
только осознанным продуктовым решением, код придётся писать заново (старый лежал
в гите до 143: своп через временный sentinel, леджер, инвалидация кэшей).

## 10. Открытые вопросы

1. **Линия `posts`** — не планируется: посты в тредах, вероятно, уйдут из продукта.
   Номер понадобится, только если посты останутся. Пока посты не трогаем вообще.
2. **Форумный `#N` в треде и цитаты `>>5`** — это **свой счётчик внутри треда**, а не
   `posts.public_id` (тот глобальный по сайту). Отдельная маленькая колонка, если понадобится.
3. **Один namespace или линии.** Сейчас номер уникален только внутри типа, значит маршрут
   без префикса (`/x/12345`) невозможен. Если нужно единое пространство — понадобится общий
   счётчик. Выбор осознанный.

## 12. Заметки на будущее

- **Медиа-ключи остаются на UUID** (`<userID>/…`): это не «долг» public_id, но переезд на
  числовые ключи — отдельная большая задача с миграцией объектов в S3.
- **«Скрыть аватар» — косметика на уровне API, а не файла:** `HideAvatar` обнуляет
  `avatar_url` в ответе (`profiles.go:321,342,461,480`), но объект лежит в публичном бакете
  `avatars` и отдаётся анонимно. Это реальнее долг приватности, чем схема нумерации.
